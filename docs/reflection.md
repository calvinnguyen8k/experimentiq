# ExperimentIQ Implementation Reflection

Week 4 Graded Assignment 4.2 | 23 November 2026

I developed ExperimentIQ as an AI-assisted experiment-planning workbench for Product Managers and Growth Analysts. I used Codex to support specification, implementation, testing and deployment. The central design decision was to separate language interpretation from numerical calculation. OpenAI extracts facts, proposes a design and critiques risks through separate structured calls. Python calculates sample sizes. Explicit inputs, unconfirmed extractions, model suggestions and deterministic results retain different roles throughout the workflow.

The most useful product lesson came from trying to move through the application. After extraction, I could not find the next step. Adding a design screen still left another incomplete journey. This feedback led to a four-stage workflow with destination-labelled Next buttons, explicit confirmation and back navigation. A complete synthetic example makes the app easier to try. Editing earlier inputs clears later results so an old calculation cannot appear to support a changed plan.

Numerical reliability required more than a convincing AI explanation. The engine supports independent two-arm continuous and binary planning approximations. Tests compare counts and rounded-allocation power with Statsmodels. Missing baselines and unsupported designs produce no fabricated sample size. The review endpoint recalculates statistics on the server rather than accepting a client-supplied result. The critic can identify concerns but cannot overwrite the calculation.

Testing combined 123 backend tests, 14 browser tests and 20 synthetic live-provider evaluation cases. The initial evaluation exposed unclear annotations and missing eligible-population extractions. The earlier runs were retained, the annotations were clarified and the extraction prompt was revised. The final development run produced 60 validated stages, but keyword matching cannot establish that a risk explanation or severity is correct. A human-reviewed benchmark remains a necessary improvement.

Deployment introduced different problems from local development. Render required payment information even for the attempted free service, so the app and API were deployed separately on Vercel Hobby. A test-only Python configuration file initially caused Vercel to skip runtime dependencies; correcting packaging resolved the startup error. Shared Redis quotas now survive function restarts, and quota failures reject new work. Both public services were verified, and a fresh browser session completed real AI calls through report download. Free hosting still does not make OpenAI usage free.

The result is a working planning MVP, not evidence of market fit or a guarantee of experimental validity. Competitor research and my usability feedback support further investigation, but independent user testing is still needed. Next, I would observe intended users completing a planning task and evaluate risk detection against human-reviewed cases before adding scope. The main lesson is to verify the complete journey while keeping uncertainty visible: a useful AI product needs clear interaction, tested calculations and claims that match the evidence.
